# Read-only economy/production integration review

Reviewed `research/berber0110/ai/berber_ai_economy.scar` and `berber_ai_production.scar` against the approved design and `INTERFACES.md` on 2026-10-18. Findings refer to the source snapshot read at approximately 20:28 local time; owners were notified and may have subsequently repaired it. No reviewed implementation or test files were edited by this reviewer.

## Actionable findings

1. **[P1] Knight observation type causes a runtime error in outpost funding.** Economy line282 compares `(st.enemy_knights or 0)>0`. Military `Observe` publishes `st.enemy_knights` as a boolean, true when qualifying heavy cavalry is observed. The first true observation makes this a boolean/number comparison and aborts the economy tick. Use the shared boolean consistently (or explicitly standardize a count contract in both modules); test the actual military-to-economy integration rather than a numeric fixture.

2. **[P1] Dedicated trade construction reads a record field from an entity handle.** Economy lines485 and488 access `st.trade_target.pos`. The shared contract and military implementation supply a native entity handle, not a `{pos=...}` contact record. Depending on native handle representation the field access errors or returns no position, so the dedicated trade Market never starts and production's trader path stays disabled. Validate `st.trade_target` and get its position via `Entity_GetPosition`. The existing trade test uses a fabricated `{pos=...,id=999}` record and therefore misses this contract violation. Revalidate a cached target before querying its position.

3. **[P1] An established healer prevents replacement of a dead religious Imam after wounds heal.** Production line129 requests `2+(st.needs_healer and 1 or 0)` monks. After a third Imam has the stable healer role, `Observe` clears `needs_healer` when nobody is wounded. If either religious Imam then dies, the remaining site/relic Imam plus healer already meet target2, and the missing religious role is never replaced. Count the still-living assigned healer separately when computing the total, while preserving demand-only creation when no healer exists. The military role map intentionally keeps a living healer independent of the two religious roles.

4. **[P2] Second-TC miners do not honor the approved four-food/four-gold split.** Economy lines295-305 accept all sorted eligible food/gold IDs until eight are selected; there is no four-per-role limit. With early food IDs, all eight can come from food. The approved implementation default explicitly selects four food and four gold. Lines299-300 also automatically reuse preexisting temporary Tent miners before testing their prior resource, so a wood-role Tent miner can enter the TC crew even though the TC group is constrained to food/gold. Keep prior resource identity and select each half explicitly.

5. **[P2] Tent temporary mining uses three workers instead of the approved eight-worker job.** Economy line412 calls `mine_stone(...,math.min(3,st.live.villager or 0),false)`. The approved default requires reuse of an eight-worker temporary mining group when a Tent stone purchase cannot be funded. This affects timing and the agreed economy distribution. Preserve job identity and prior roles while funding the missing stone; restore those roles afterward.

## Pending-command integration checks

Economy line219 unlocks saving immediately when `Construct` returns true. Lines199 and202 also treat a pending landmark request as sufficient to bypass saving. Root's shared contract says `Construct` returns an issued normal command with a pending ledger; an accepted command is not necessarily an observed native foundation. If root does not synchronously confirm placement, a rejected/deferred landmark can unlock all new spending for the ledger timeout even though no foundation exists. Review root's final confirmation/retry semantics and add a cross-module rejected-foundation test; the existing economy fixture creates a foundation synchronously and cannot prove the native case. This is an integration risk rather than an assumed final engine defect while root's engine boundary remains under construction.

Likewise, economy line337 clears the one-time second-TC need on command acceptance. If root exhausts retries without materializing a TC, the one-time flag can leave the expansion permanently abandoned. Keep the decided need until a real foundation is observed, or provide a failure callback that reopens it. Root's final ledger may already address this; verify the real integration.

## Behavior checked without an actionable finding

Shared-budget sequencing funds housing/villagers before savings and discretionary spending. `return_jobs=true` is supplied to age-up, house, opening and expansion construction, with the actual restoration delegated to root's engine job owner. Accepted pair halves are retained, rejected/expired halves are retried, and missed expansion intervals do not create a backlog. Military producers request <=20m influence checks from complete Tents/landmark; ordinary Tent caps exclude the landmark. Farm funding precedes extra paired producers. Production research/production respects `saving_age`, filters live producer handles, uses a single Spend budget, gives core upgrades priority, sorts random Blacksmith candidates, restricts traders to the dedicated producer and excludes that market from ordinary army production. Feudal ram requests use the normal blueprint, engineering prerequisite and reserved archer builders.

The currently available full domain suite passed 86/86 after the military worker's final tests; that does not remove the integration findings above because the isolated economy/production fixtures differ from the military field contracts. Engine costs, command acceptance and native navigation remain separate acceptance gates.
